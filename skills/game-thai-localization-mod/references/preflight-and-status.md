# Preflight and Evidence Status

## Contents

- Preflight contract
- Work status and required evidence
- Evidence record

Read this before changing or packing game files. Save the preflight record beside
the working translation, not inside the live game directory.

## Preflight contract

Record these values before editing:

- game name, install root, executable/process names, and every live target path;
- intended runner, Steam/account identity, process namespace, config root, and
  whether the game library is shared with another runner;
- engine/container type and the logical-source to physical-archive/member map;
- loader contract: archive priority, signing/encryption policy, required launch
  options/plugins/selectors, and where each setting persists;
- SHA-256 and byte size of each source archive and extracted source file;
- pinned source and target encoding, including BOM policy;
- runtime-test policy: permitted, forbidden, or manual-by-user;
- every backup/staging root, retention limit, existing count, and bytes used;
- free bytes on each filesystem involved and calculated required headroom;
- current story/scene scope, speaker/context notes, and spoiler boundary;
- glossary, locked fields, ID fields, text fields, and known byte/line limits.
- expected changed member, IDs, and fields for each target archive;
- alternate-archive override policy and companion/censored-field policy.

Treat a changed source hash, install path, archive map, or runtime-test policy as
a new preflight. Stop and refresh the record rather than silently reusing stale
assumptions.

Hash and compare each source archive/member that will receive a translation.
Matching member names do not prove matching source text; record archive-specific
source/Thai overrides when needed.

Calculate required headroom before packing:

    rollback copies
    + packed candidates
    + unpack-and-diff trees
    + same-filesystem install temporary files
    + tool-generated scratch space
    + safety margin

Measure the relevant filesystem, not only the workspace filesystem. Include
backups generated by helper scripts in both the inventory and retention count.

Use this default retention contract unless the user explicitly overrides it:

- one verified rollback set;
- zero staging, unpack, candidate, snapshot, or regenerable working-data backup
  trees after a committed byte-verified install;
- retain small journals, manifests, hashes, and QA reports;
- retain all material required by a prepared, installing, restoring, failed, or
  otherwise incomplete transaction until recovery reaches a verified terminal
  state.

Before packing, rotate verified terminal artifacts that exceed the contract and
record the exact removed paths and freed bytes. If the inventory remains over
the limit because an artifact is unsafe to delete, stop before creating another
candidate or rollback set.

## Work status and required evidence

Advance monotonically through these statuses:

1. draft
   - Translation exists, but contextual review and structural validation are
     incomplete.
2. translated
   - All rows in the declared pass are translated or explicitly classified as
     intentionally unchanged, with glossary and spoiler boundary applied.
3. reviewed
   - A context-aware pass checked voice, terminology, reveals, Thai fluency,
     and representative UI length risks. Record reviewer/check scope.
4. static-valid
   - The central validator passes; pack-unpack-diff checks pass for every
     candidate archive; the source-to-working field delta matches the declared
     IDs/fields for every target; hashes and validation reports are current.
5. installed-and-byte-verified
   - The stopped game was updated transactionally; every installed target
     matches its verified candidate hash/bytes; the install journal is complete.
6. runtime-proven
   - A permitted runtime test proves the game boots and reached the tested Thai
     surfaces, with current screenshot/log/process evidence from the intended
     runner. Record its account/config root, normal-launch command line, and
     loader log or exact handle evidence for the installed payload.

Each status inherits all evidence from prior statuses. Never skip a status in
reporting. A manual runtime test by the user does not become runtime-proven until
the result, tested build/hash, and runner are recorded. Proof from Playbeam does
not transfer to host Steam, or vice versa, when account/config or loader settings
differ. If launch permission is withheld, stop at installed-and-byte-verified
and say runtime-unverified.

## Evidence record

Keep a small JSON or equivalent record containing:

- current status and timestamp;
- source/candidate/installed hashes;
- runner/account/config root and loader settings used by the normal launch;
- validator report path, field-delta audit, and archive diff evidence;
- reviewed scope and unresolved classifications;
- install journal path and rollback path;
- runtime policy and, only when permitted, runtime evidence paths.

Do not use an old screenshot, manifest, verifier output, or hash to advance a
new candidate.
